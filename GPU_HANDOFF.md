# GPU workstation handoff — Paper 1

**Current stage: CPU baseline + deterministic program synthesis. No GPU is needed for v0.9.** These are research experiments, not a verified real-time collision avoidance controller. Do not send v0.9 velocity commands directly to hardware.

## 1. Verify CPU baseline on your PC

Python 3.10+ is recommended (3.11+ preferable). This version uses **no external Python dependencies**.

Linux / macOS:

```bash
python3 -m unittest discover -p 'test_*.py' -q
python3 run_prefix_tree_v09.py --repeats 3 --holdout 100
python3 run_branch_stress_v09.py --siblings 40 --repeats 3
```

Windows (PowerShell):

```powershell
py -3 -m unittest discover -p "test_*.py" -q
py -3 run_prefix_tree_v09.py --repeats 3 --holdout 100
py -3 run_branch_stress_v09.py --siblings 40 --repeats 3
```

The saved JSON/CSV in `synthesis_results_v09/` is generated by these commands. Runtime will depend on the CPU and Python version; do not compare wall-clock seconds across machines without recording the hardware/software configuration. The resulting frozen DSL programs should match across the three execution backends.

## 2. Workstation information before installing Isaac Lab

Record these on the PC and keep the text output alongside your benchmark:

- GPU model and VRAM: `nvidia-smi` (NVIDIA hardware)
- OS version, CPU model, RAM: system information tools
- Python version: `python --version`
- CUDA/driver version: shown in `nvidia-smi` (driver CUDA number does not itself prove a matching toolkit install)
- Available disk space, simulation and camera requirements
- Physical robot make/model, DoF, controller interface, and camera type

Isaac Sim / Isaac Lab version and driver requirements change, so use the **official compatibility and installation guides for the selected release** before setting up environments. Pin the exact versions in a new file; keep this baseline environment dependency-free.

## 3. GPU/Isaac integration contract (proposed, not yet implemented)

Create an `IsaacChamberAdapter` implementing:

```python
class ChamberAdapter:
    def reset(self, seed: int): ...
    def observe(self): ...  # robot state, goal, obstacle pose/velocity
    def step(self, action): ...
    def get_state(self): ...  # serializable checkpoint when supported
    def set_state(self, state): ...
    def collision_report(self): ...
```

Run **identical static test cases** using CPU geometry and simulated geometry, then test moving boxes, wall reflections, collision detection between frames, and deterministic reset. GPU parallelism changes when and how states are managed; an undo log of host Python fields is **not** a GPU simulator state rollback mechanism. If exact simulator state cloning is not supported, use deterministic reset-and-replay or independent simulation instances; do not claim exact backtracking on the GPU.

## 4. Experiments to run before articulated-arm or real-robot work

1. Increase chamber counts and obstacle density; include intentionally unsolvable chambers and moving obstructions.
2. Introduce noisy state observations, latency, and unknown obstacle motion; measure timeouts and collisions.
3. Compare OOPS code reuse with fresh search and with SIPP, space-time A*, and standard receding-horizon planning under comparable compute budgets.
4. Report p50/p95/p99 planning latency, goal success, collision/interventions, budget consumption, memory peak and repeated-run variance.
5. After these tests, move from spherical agent to robot joint-state planning and full-arm collision checking, with a physically independent safety controller.

## 5. Reproducible artifact layout

- `oops_prefix_tree_v09.py`: lazy prefix-trie evaluator
- `run_prefix_tree_v09.py`: curriculum timings + 20/100-scene holdout
- `run_branch_stress_v09.py`: branch-heavy stress test
- `test_oops_v09.py`: equivalent outcomes and replay parity
- `synthesis_results_v09/`: JSON and CSV from repeated experiments
- `PREFIX_TREE_V09_SPEC.md`: architecture, limitations, and methods

Optional local hardware preflight: `python pc_preflight.py --output pc_hardware_report.json`. The resulting report contains your Python interpreter path and GPU details; review it before sharing because local executable paths may identify your account. No report is uploaded or sent anywhere by the script.
